# Authoring in the CMS

A guide to the admin at `/admin` — what changed in the recent rework, why, and how to build a
lesson now. Written for whoever is writing the content, not for developers.

The companion to this is [`content-backlog.md`](./content-backlog.md), which lists the specific
things in the existing content that need an author's decision. This document is about the tools;
that one is about the to-do list.

## The short version

Nothing a learner sees was supposed to change, and nothing did. What changed is underneath: the
content used to be a transcription of an old export — one rigid shape per screen, media referenced
by pasted URLs, vocabulary repeated wherever it was used. Now it is modelled properly, which means
you can build a screen that nobody anticipated without asking a developer for one.

Three ideas carry most of it:

1. **A screen is a list of blocks**, not a single fixed thing.
2. **A word is authored once** in Vocabulary and referenced everywhere else.
3. **A file is a real file** in Media, picked from a list, not a URL typed into a box.

## A lesson is a list of screens

Open a lesson and you will see **Exercises**. One exercise is one screen — what a learner sees
before tapping Next.

Inside each exercise is **Components**: the blocks that make up that screen, in order. This is the
change that matters most. A screen used to be allowed exactly one block, so every new layout needed
a developer to invent it. Now a prose introduction followed by the exercise it sets up is *one
screen with two blocks*, and you can build that yourself.

Drag exercises to reorder them. Drag blocks within an exercise to reorder those.

> **Shuffle Exercises**, on the lesson, varies the order of consecutive practice screens of the same
> kind, per learner. Screens that present material never move. Turn it off where the order teaches
> something.

## The block library

Eleven blocks, in two groups. The group is not decoration — it is what tells the shuffle which
screens are interchangeable.

### Content — material to read or watch

| Block | What it is |
|---|---|
| **Prose** | Text. Four styles: Plain page, Note card, Fun fact, Life tip. |
| **Dialogue** | A two-speaker conversation. Each line says which speaker it belongs to. |
| **Video** | A video, with optional supporting text. |
| **Grammar point** | One or more points, each with an explanation and examples. |
| **Vocabulary** | A set of words. Four layouts: List, Flashcards to flip, Image grid, Spotlight one character. |
| **Figure** | An image or audio clip with a caption. |

### Practice — things the learner answers

| Block | What it is |
|---|---|
| **Match pairs** | Pair things up. Word ↔ meaning, word ↔ reading, hiragana ↔ katakana, or audio ↔ word. |
| **Listen and choose** | Play audio, pick the answer. The answer can be the written word or a picture. |
| **Build a sentence** | Assemble a sentence from parts. Can present as authored or converted to romaji. |
| **Speak and score** | The learner says it; the app scores against a reference recording. |
| **Multiple choice** | A question and options. |

Every block shows a meaningful summary when collapsed, so a long exercise list stays readable.

### Two that used to be invented for you

The **stroke-order screens** and the **practice batches** used to be generated by the player from a
table in the code. They are ordinary authored screens now. What you see in the Exercises list is
exactly what a learner gets — which also means if you want a stroke-order screen somewhere new, you
add a Vocabulary block with the *Spotlight one character* layout.

## Vocabulary: author a word once

**Vocabulary** is its own collection. A word lives there with its readings, meaning, audio and
image, and lessons *reference* it rather than restating it.

The point: fix a word's audio once and it is fixed in every lesson that uses it. Before, the same
word appeared in several lessons with its details retyped each time, so they drifted.

A term carries: the Japanese, katakana, reading and romaji; furigana as base/ruby pairs; an English
meaning; part of speech; JLPT level; stroke count and stroke-order image; tags; and free notes.

Not every field applies to every word — fill what is true. `content:verify` reports which fields are
missing across the catalogue, and that report is the backlog, not a set of errors.

## Rich text, furigana and word references

Text fields are a proper editor now, not plain strings. Inside one you can add:

- **Furigana** — attach a reading above any run of characters.
- **A word reference** — point at a Vocabulary entry. It renders with that word's reading and audio,
  and follows the word if you later change it.
- **Callouts** and **example sentences** as their own blocks.
- **Images**, with a caption.

One rule worth knowing: a word reference renders *nothing at all* if the word it points at is
deleted. It does not show a broken link or an id — it silently disappears. That is deliberate (a
learner should never see a database id) and it is why deleting vocabulary is restricted to admins.

## Media

Upload a file once in **Media**, then pick it from the media field of whichever block needs it.

Files used to be referenced by URL strings pasted from elsewhere, which is how a missing file became
the literal text `PLACEHOLDER_AUDIO_URL` and how renaming one file quietly broke six blocks. Now a
media slot either points at a real file or is empty, and empty is countable.

**Alt text is required for images** — what the image shows, for screen readers. It is not required
for audio or video, where it means nothing. The rule is enforced on save rather than asked for
politely, because roughly half the existing catalogue has an empty alt from the original import.

You can search Media by filename, alt text or caption. Worth knowing because much of the catalogue
arrived with names like `Screenshot_2026-08-14_at_11-42-03.png` — searching what the picture *shows*
works better than searching what it is called.

## Drafts, autosave and publishing

**Your work saves itself.** Autosave runs a few times a second while you type, so there is no Save
button to forget. The header shows when it last saved.

**Saving is not publishing.** An autosaved lesson is a *draft*: it is stored, it is yours to come
back to, and it is not on the site. **Publish changes** is what puts it live. A lesson that has
never been published is not visible to learners at all — that is how an unfinished lesson stays
unfinished safely.

**You can go back.** Every document keeps its last 20 versions, under the **Versions** tab. Older
ones are dropped as new ones arrive, so it is a working undo history rather than an archive.

**Live preview** shows the lesson beside the editor as you type, in whichever player the lesson's
Format selects. The **preview** button opens the same thing full-width in a new tab.

## What you can and cannot do

Two roles.

**Editor** — create, edit and publish everything: lessons, courses, vocabulary, media, resources.
This is what authoring needs, and it is the default.

**Admin** — the above, plus deleting content and managing who has an account.

If a Delete button refuses, that is the role, not a bug. Deletion is separated out because it is the
one action with no undo: deleting a word blanks it out of every lesson that referenced it, and
deleting a media file removes the file itself. Ask an admin, who can also tell you what else pointed
at the thing.

Everyone who signs in can see the full content and the list of who else has an account.

## When something looks wrong

- **A word shows no audio or no image.** The term probably has an empty media slot. Open it in
  Vocabulary — fixing it there fixes every lesson using it.
- **A screen renders blank.** Usually an empty block. The collapsed row label shows what a block
  contains, so an empty one is visible without opening it.
- **A change is not on the site.** Check whether it was published. Drafts save constantly and go
  live never.
