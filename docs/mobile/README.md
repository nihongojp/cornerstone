# Mobile: iPhone app plan and status

Status: **Phase 1 in progress** on `feature/mobile-ios`. Last updated 2026-10-29.

The full plan, with options, risks, and the Apple paperwork, is the
`nihongo-iphone-app-plan.md` doc in the NihonGo Claude Project. This file is the
in-repo summary and the running status.

## Approach

Wrap the web app in a native shell with Capacitor. Do not rewrite it. The hard
parts of this app are web code (the D3 map, drag-and-drop, tracing canvas, MUI),
and all of them run as they are inside a WebView.

Three phases:

- **Phase 0** — mobile constraints on the Next.js app: safe areas, viewport,
  route handlers for learner data, bearer auth. *Partly done; see below.*
- **Phase 1** — PWA: manifest, icons, service worker, offline page, install
  hint. *Done, pending a device test.*
- **Phase 2** — Capacitor shell for the App Store: static export mode, native
  plugins, offline lessons, push. *Not started.*

## What is in the repo now

- `src/app/manifest.ts` — web app manifest, served at
  `/manifest.webmanifest`.
- `src/app/(app)/layout.tsx` — `viewport` export (`viewportFit: "cover"`,
  theme color) and `appleWebApp` metadata.
- `public/sw.js` — service worker. Precaches `/offline` and the icons, caches
  static chunks and media, never touches `/api`, `/admin` or previews.
- `src/components/pwa/RegisterServiceWorker.tsx` — registers the worker in
  production builds only.
- `src/app/(app)/offline/page.tsx` and `OfflineNotice.tsx` — the page the
  worker serves when a navigation fails offline.
- `src/components/pwa/InstallHint.tsx` — iOS Safari "Add to Home Screen"
  nudge. Hidden once installed, dismissable for 30 days.
- `src/components/SiteChrome.tsx`, `Footer.tsx` —
  `env(safe-area-inset-top/bottom)` padding.
- `public/icons/*` — **placeholder** icons, generated by
  `scripts/mobile/make-placeholder-icons.py`.
- `next.config.ts` — `no-store` headers on `/sw.js`.

### Testing the worker locally

The worker does not register under `next dev` on purpose. To test it:

```bash
npm run build && npm start
```

Then open the site, confirm `nihongo-sw-v1-precache` exists in DevTools →
Application → Cache Storage, set the network to Offline, and navigate. You get
the `/offline` page.

When you change `public/sw.js`, bump `CACHE_VERSION` inside it. The `activate`
step deletes every cache that does not carry the current version.

## Open items before Phase 1 is done

1. **Real icon.** Replace the four files in `public/icons/`. Keep the names.
   Requirements: 1024×1024 source, flat, no transparency for the Apple one.
2. **Device test** on a real iPhone in Safari: install, open from the Home
   Screen, check the header sits below the notch, finish one lesson, go
   offline, confirm the offline page.
3. **Player safe areas.** The `(player)` route group has no SiteChrome, so its
   own top bar needs `env(safe-area-inset-top)` once we see it on a device.
4. **Inputs at 16px.** iOS zooms the page when a focused input has text under
   16px. Check the auth form and the exercise inputs.

## Phase 0 items still open

These matter for Phase 2, where the UI runs as a static export inside the app and
has no server of its own.

1. **Learner data through route handlers.** Progress and attempts are saved with
   Server Actions today (`src/features/learning/actions.ts`). The mobile bundle
   cannot call a Server Action, so the same operations need `/api/*` route
   handlers. Keep the actions for the web; the handlers call the same functions.
2. **Content through a route handler.** `src/lib/content/content.ts` reads
   Payload in-process. The mobile bundle needs `/api/content/<section>` with the
   same cache tags.
3. **Bearer auth.** The Capacitor WebView origin is `capacitor://localhost`, so
   the Better Auth cookie from `learn.nihongojp.com` is third-party and gets
   dropped. Add the Better Auth `bearer` plugin next to cookie sessions. Web
   keeps cookies; mobile uses the token.
4. **Sign in with Apple.** The app offers Google sign-in (`GOOGLE_CLIENT_ID`).
   App Store Guideline 4.8 then requires Sign in with Apple as well. Better
   Auth has an `apple` provider; it needs the Apple Developer account first.

## Not code: Apple paperwork

Start these now. They do not wait for the code.

- D-U-N-S number for the nonprofit (free, Dun & Bradstreet; weeks of lead time).
- Enroll the nonprofit in the Apple Developer Program as an organization and
  request the fee waiver (US nonprofits that ship only free apps pay $0).
- Decide the public product name and bundle ID. "Cornerstone" is a codename.
- Privacy policy and support pages on nihongojp.org.
- A Mac with Xcode 26. Apple accepts only Xcode 26 builds since 2026-04-28.
